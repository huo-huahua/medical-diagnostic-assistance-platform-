## 一、工程化与可维护性

### 1. 自动化测试 —— 当前 **0 个测试** ⭐

> ✅ **已完成（2026-10-04）**：现有 **427 个 pytest 用例**（10 个文件），一次运行约 60–90 秒。
> 覆盖切块窗口约束、LLM 网关四道闸门、三道拒答闸门、标签语义与阈值、批量汇总一致性、
> 三路径对比、**8 家服务商接入层与离线演示通道**、认证与账号隔离、响应信封、默认密钥校验。
> 测试强制关闭真实外部 API，不产生费用。
> 用例分布与「每个测试在防哪个 bug」见 [`TESTING.md`](TESTING.md)。
>
> 顺带修掉的问题：测试基建本身踩到的坑（`.test` 保留域名被 email-validator 拒绝、
> Windows 上 SQLite 打不开 `/tmp` 路径、限流器单例被套件自己触发）都记录在 `TESTING.md` §4。

**现状**：全仓库没有 `tests/` 目录，也没有任何 `*.test.ts`。约 9000 行代码零测试覆盖。

**风险**：已经吃过亏 —— 之前修的两个真 bug（总览页白屏、SSE 返回空响应）都属于"改一处崩一处"，全靠人工打开浏览器才发现。没有测试，每次改动都在赌。

**方案**（按性价比排序）：
1. 后端 `pytest` 先覆盖 3 条主链路：注册登录 → 预测 → 问答
2. 加"黄金样本回归测试"：固定几组特征向量，断言判定与概率区间不变（防重训/重构后静默改判）
3. 把之前手工验证的 12 条 RAG 拒答用例固化成参数化测试

**收益**：改动不慌，开源贡献者敢提 PR。**成本 M**。
**注意**：测试要换内存/临时数据库，别污染 `bcdx.db`。

### 2. CI 流水线 ⭐

> ✅ **已完成（2026-10-04）**：`.github/workflows/ci.yml`，两个独立 job——
> **后端**（安装依赖 → 从已提交的 CSV **重训模型产物** → 打印切块统计并在 `oversize > 0` 时提前失败 →
> pytest + 覆盖率）与**前端**（`npm ci` → `typecheck` → `build`）。
> 因 `ml/registry/models/*.joblib` 不入库，CI 顺带**持续验证训练管线本身**；
> 训练全程固定随机种子，已实测重跑后除 `generated_at` 外逐字节一致。详见 [`TESTING.md`](TESTING.md) §5。

**现状**：无 `.github/` 目录。

**方案**：GitHub Actions 一个 workflow 跑三件事 —— 后端 `pytest`、前端 `tsc --noEmit` + `vite build`、以及"能装起来"的冒烟检查。

**收益**：PR 自动拦截；README 可挂 build 徽章（开源门面）。**成本 S**。

### 3. Docker / Compose 一键部署 ⭐

**现状**：`OPTIMIZATION_1.0.md` 的技术选型写了「部署：Docker Compose」，但仓库里**没有任何 Dockerfile 或 compose 文件**（原计划的 `infra/` 目录已作为空目录删除）。

**影响**：开源项目最大的流失点就是"怎么跑起来"。现在别人要装 Python + Node + 一堆依赖，而 `docker compose up` 只要一条命令。

**方案**：
- `backend/Dockerfile` —— 注意 **sentence-transformers 模型要预下载进镜像**，否则首次启动需联网（这是最容易踩的坑）
- `frontend/Dockerfile` —— 多阶段构建 → nginx 静态托管
- `docker-compose.yml` —— 后端 + 前端 + 可选 Redis（配合第 11 项）

**收益**：部署门槛从"半小时踩坑"降到"一条命令"。**成本 M**。

---

### 4. 依赖未锁版本 ⭐

**现状**：`backend/requirements.txt` 用范围约束：

```
fastapi>=0.115,<1.0
scikit-learn>=1.3,<1.6
numpy>=1.24,<2.0
```

**问题**：今天装和半年后装可能得到不同版本，指标和 API 都可能漂移（`scikit-learn` 1.3 与 1.5 在部分默认行为上有差异）。

**方案**：`requirements.txt` 保留为"声明"，另生成 `requirements.lock`（`pip-compile` 或 `pip freeze`）；文档说明"复现环境用 lock，尝鲜用原文件"。

**收益**：构建可复现，issue 排查容易。**成本 S**。

---

### 5. OCR 是**死代码** ⭐

**现状**（已核实）：`backend/app/schemas/__init__.py` 定义了 `OcrFieldOut` 与 `OcrResponse` 两个模型，但**全仓库搜不到任何使用** —— 没有 `/ocr` 路由、没有 OCR 服务、前端也没有相应页面。同时 `.env.example` 里还留着 `MAX_UPLOAD_MB=10` 这个为上传功能准备的配置。

**背景**：原毕设 cp16 是有 EasyOCR 图片识别功能的，迁移时被砍掉，但契约层没清干净。

**两条路**：
- **A. 先删掉**（推荐）：移除两个死 schema + `MAX_UPLOAD_MB`。**成本 S**
- **B. 补实现**：加 `/ocr` 路由 + 前端上传页 + 字段识别。**成本 L**
  - 好处：**最能提升易用性** —— 用户不用手敲 30 个数值
  - 若做，建议 PaddleOCR 或 RapidOCR（纯本地、中文友好、零 API 费用），并沿用现有"范围校验 + 用户确认后再预测"流程，**绝不直接采信 OCR 结果**

### 6. 数据库迁移工具未启用

**现状**：`requirements.txt` 声明了 `alembic>=1.13`，但**代码里从未引用**，也没有 `alembic/` 目录。建表走 `Base.metadata.create_all()`。

**问题**：`create_all` 只建不改。一旦改表结构（加字段、改类型），已有数据库**不会自动更新**，老用户直接报错。

**收益**：未来改表不必让用户删库。**成本 M**。

## 二、安全

### 8. `.env.example` 里的默认密钥 ⭐

> ✅ **已完成（2026-10-04）**：模板里的 `SECRET_KEY` 换成了明显占位的 `change-me-generate-with-openssl-rand-hex-32`，
> 并加了启动期校验：`ENVIRONMENT=production` 且密钥命中占位清单 / 含 `change-me`、`dev-only-secret` 等标记 → **直接拒绝启动**
> 并打印生成命令；开发环境只打一条警告，不打断本地开发。
>
> 之所以用"清单 + 标记"双条件而不是"长度不够就报错"：原来的默认值**本身足够长、还带随机后缀**，
> 长度校验放它过去。检测清单里**保留了旧的占位值**，因为已经有人把它复制进自己的 `.env` 了。
> `test_app.py` 里有一条用例**直接读仓库中的 `.env.example`**，断言"模板发的是什么，就检测得到什么"——
> 防止以后换了模板却忘了同步检测列表。
>
> 安装与配置说明见 [`LLM_INTEGRATION.md`](LLM_INTEGRATION.md) §9。

**现状**：

```
SECRET_KEY=dev-only-secret-please-change-me-in-production-2f8a91c4
ACCESS_TOKEN_EXPIRE_MINUTES=10080
```

**问题**：这个默认值**长得像真密钥**（还带随机后缀），很容易被直接复制到生产环境。一旦照抄，任何人都能用这个公开密钥**伪造任意用户的 JWT**。另外 10080 分钟 = **7 天**，且无吊销机制。

**方案**：
- `.env.example` 改成明显占位符：`SECRET_KEY=CHANGE_ME_generate_with_openssl_rand_hex_32`
- **启动时校验**：`ENVIRONMENT=production` 且 `SECRET_KEY` 未改或长度不足 → **拒绝启动**并给出生成命令
- 文档附：`python -c "import secrets;print(secrets.token_hex(32))"`

**收益**：堵住最可能的"开源部署即被攻破"路径。**成本 S**。

### 9. 审计日志只覆盖登录

**现状**：`AuditLog` 表有 **33 行**（确实在写），但代码里只有 `auth.py` 一处调用 —— 只记录注册/登录。**预测、删除记录、删除会话都没有审计**。

**方案**：在预测、删除、导出等关键动作上补审计写入（含 `user_id`、动作、目标 id、结果、`request_id`）。

**收益**：可追溯性，医疗类工具的合规加分项。**成本 S**。

---

### 10. Token 无刷新 / 无吊销

**现状**：只有 access token，7 天有效期，无 refresh token、无黑名单、无"登出即失效"。

**影响**：token 泄露后 7 天内一直有效；用户点"退出"只是前端删了 localStorage，**服务端仍认这个 token**。

**方案**：access token 缩到 15–30 分钟 + refresh token（存库可吊销）+ 登出写吊销表。

**成本 M**。纯演示可暂缓；对外提供服务则必要。

---

### 11. 限流仅单进程有效

**现状**：`core/deps.py` 的 `RateLimiter` 是**进程内**滑动窗口（`defaultdict(deque)`），代码注释自己也承认：

> "Adequate for a single-worker open-source deployment. Behind multiple workers or instances this should be swapped for Redis."

**影响**：`uvicorn --workers 4` 启动 → 实际额度变 4 倍；多实例部署则完全失效。

**方案**：抽 `RateLimitStore` 接口，内存实现 + Redis 实现，配置切换。

**成本 M**。若第 3 项做了 Compose，顺手加 Redis 即可。

---

### 12. 特征数组缺上界校验

**现状**：`PredictRequest.features: list[float] = Field(min_length=1)` —— **只有下限**。理论上可 POST 百万元素数组。

对比：`BatchPredictRequest.rows` 有 `max_length=500`，`AskRequest.question` 有 `max_length=1000`，**只有这处漏了**。

**方案**：加 `max_length=64`（当前最多 30 特征），并在服务层断言长度与 `feature_schema` 一致。

**成本 S**。

### 14. 切块策略过于粗糙 ⭐

> ✅ **已完成（2026-10-04）**：改成了**按模型真实计数单位（token）切块**，而不只是"加上重叠"。
>
> 这条比原描述严重得多——原切块按空行切分且不控长度，实测 **76 个片段里 75 个（98%）超过嵌入窗口
> （128 token），最长的 305 token**，尾部被**静默截断**且不报错。按字符数折算救不了它：实测中文医学文本的
> 字符→token 比值在 0.724–0.843 之间波动，没有固定的换算系数可用。
>
> 现在的做法：窗口运行时从模型读取；每小节的额度**减去它自己标题路径的 token 消耗**；
> 切分时**每刀重新测量**（`_clamp`）而非按比例折算；相邻片段 40 字符重叠且**重叠会被裁剪到剩余空间以内**；
> 过短小节合并并保留被吞掉的标题文字。启动时复核每个片段，把 `oversize` 暴露到 `/health`（现为 **0**）。
>
> 附带解决：检索用片段粒度、引用用段落粒度（`group_passages`），避免同一标题重复出现。
> 完整说明见 [`KNOWLEDGE_BASE.md`](KNOWLEDGE_BASE.md) §3，回归测试见 [`TESTING.md`](TESTING.md) §3.1。

**现状**：`parse_markdown_chunks()` 的实现是 `re.split(r"\n\s*\n", raw)` —— **按空行硬切**。

**问题**：
- 段落长度不受控（几十字到上千字都有）
- **片段之间零重叠** → 答案跨段落时缺少上下文
- 不识别语义边界（完整论述被空行切成两半）

**方案**：
- 按标题层级 + 句子边界切，目标 300–500 字，**相邻片段重叠 15%**
- 把所属标题拼进片段文本作为上下文前缀，提升召回
- 可选：标题单独建"摘要块"，提高概念类问题的命中率

**收益**：召回率与答案完整性同时改善。**成本 M**。

### 15. 只有向量检索，没有混合检索与重排

> ✅ **已完成（2026-10-04）**：稠密检索 + **自实现 Okapi BM25** 两路召回，**RRF**（`k=60`）融合，**默认开启**；
> CrossEncoder 重排（`bge-reranker-base`）已接好但**默认关闭**。工具 `_tools/eval_retrieval.py` 可复跑 A/B。
>
> 实测（15 个探针 + 4 个反向探针，期望小节从语料里查出而非手写）：
>
> | 模式 | hit@1 | 进 top-5 | 误拒答 | 平均耗时 |
> |---|---|---|---|---|
> | `dense`（旧行为） | 9/15 | 12/15 | **4** | ~24 ms |
> | `hybrid`（默认） | **13/15** | 13/15 | **0** | ~25 ms |
> | `hybrid+rerank` | 13/15 | 15/15 | 0 | ~2241 ms |
>
> **真正修好的是"误拒答"**：那 4 个问题在旧模式下**全部被拒答**，且拒答它们的是**词法覆盖闸门**而非相似度闸门
> （最高余弦 0.43–0.61，远高于 0.30）。dense 把"一个内容词都不重合的小节"排到第一，闸门于是如实拒绝作答——
> 坏掉的是排序，拒答是诚实的。BM25 把含该词的小节顶到第一，两道闸门同时满足。
>
> **重排为什么默认关闭**：它买到两格 top-5、**top-1 一格没变**，而延迟涨到约 **90 倍**。本地路径是本项目
> 承诺"快且零成本"的那条路，让它比被对照的真实模型调用还慢是看得见的倒退。一行配置可开。
>
> 顺带解决：病种过滤改为跑在**融合之前**（`in_scope` 在每个召回器内部生效），否则 BM25 能把别的病种捞回来；
> 删掉 `breadcrumb` 加权（`embed_text` 已含标题，BM25 现在也会给标题打分，原来的加权是重复的）。
>
> 完整原理、两个"反直觉"的取值（余弦闸门取命中最大值、词法闸门只读 `hits[0]`）见
> [`KNOWLEDGE_BASE.md`](KNOWLEDGE_BASE.md) §4。

**现状**（本轮修改前）：`sentence-transformers` 嵌入 + `FAISS IndexFlatIP` 纯向量检索，`RAG_TOP_K=5`（本文档早先写成 4，是陈旧的）。

**问题**：
- **专有名词/缩写/数字**（如 "BI-RADS 4A"、"0.1701"）向量检索常不如关键词检索准
- `IndexFlatIP` 是暴力检索，语料变大后延迟线性增长

**方案**：
1. 加 **BM25 关键词检索**，与向量得分融合（RRF 或加权），显著改善缩写与数字类问题
2. 引入**重排模型**（如 `bge-reranker-base`，本地免费）对 top-20 重排取 top-4
3. 语料上量后把 `IndexFlatIP` 换成 `IndexHNSWFlat` 或 IVF

**收益**：检索准确率通常有明显提升。**成本 M**。

## 五、前端体验

### 20. 缺少全局错误边界 ⭐

> ✅ **已完成（2026-10-04）**：`components/ErrorBoundary.tsx`（class 组件 + `getDerivedStateFromError` /
> `componentDidCatch`），**两层**接入：应用外壳一层（`main.tsx` 包住登录守卫），**按路由**一层
> （`AppShell` 包住 `<Outlet />`）。错误页提供「重试 / 返回总览 / 复制错误详情」，重试会先清 React Query 缓存

>
> 两个不做就会白做一层的细节：路由层必须带 `key={location.pathname}`，否则一旦出错**切页仍是错误页**；
> **错误边界只能防止"整站白屏"，不能修复底层 bug**——这一点写在组件注释里，免得后来者以为它是万能的。

**现状**：全前端**没有 `ErrorBoundary`**（搜不到 `componentDidCatch` / `getDerivedStateFromError`）。

**问题**：任何组件抛异常 → React 卸载整棵树 → **整站白屏**。这不是假设，**上次总览页白屏就是这么发生的**（`health.data.llm.cache` 读空）。

**方案**：加 `ErrorBoundary` 包住路由出口，展示友好错误页 + "重试 / 返回首页 / 复制错误详情"；再按页面粒度包一层。

**收益**：单页出问题不再拖垮全站。**成本 S**，性价比极高。
