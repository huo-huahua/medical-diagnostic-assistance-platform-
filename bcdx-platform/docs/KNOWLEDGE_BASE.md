## 二、病种归属是自动推断的

**规则：文件名决定病种**（`app/services/rag_service.py` 的 `_DISEASE_HINTS`）。

| 文件名包含 | 归属 |
|---|---|
| `breast` | `breast` |
| `heart` / `cardiac` | `heart` |
| `disclaimer` | `general` |
| 其他 | `general` |

也可以在文件顶部用 front matter **显式覆盖**：

```markdown
---
disease: heart
---

# 正文从这里开始
```

front matter 会被剥离，不会进入可检索正文（否则 `disease: heart` 这几个字会变成可被检索的噪声）。

## 三、切块策略：为什么不能按字符数切

这是本项目最隐蔽的一个 bug，值得完整讲一遍。

### 3.1 问题：嵌入模型会**静默截断**

`sentence-transformers` 在文本超过模型的 `max_seq_length` 时**不报错、不警告，直接截断**。本项目用的 `paraphrase-multilingual-MiniLM-L12-v2` 窗口是 **128 token**。

原先的切块逻辑**只按空行切分**（`re.split(r"\n\s*\n", raw)`），既不识别标题层级，也不控制片段长度——切出来多长，完全取决于原文段落碰巧写了多长。看起来没什么问题——直到拿真实 tokenizer 量了一遍：

> **76 个片段里有 75 个（98%）超过 128 token 窗口，最长的达 305 token。**

也就是说，**几乎每一条知识条目的后半段都是检索不可见的**，而且日志里一行错误都没有。用户问的东西恰好写在条目尾部时，系统会检索不到，然后拒答——看起来"知识库没写"，实际上写了，只是被吃掉了。

### 3.2 为什么不能用"平均字数"折算

实测中文医学文本的 **字符 → token 比值**：

| | 比值 |
|---|---|
| 平均 | 0.724 |
| 最大 | 0.843 |

也就是说约 150 汉字 ≈ 128 token，但**比值本身在波动**。用 `max_chars` 反推 token 数，永远无法保证不越界——只能保证"大部分情况下不越界"，而"大部分"正是这个 bug 存活下来的原因。

**结论：切块必须在模型真正计数的那个单位上做。**

### 3.3 现在的做法

```
window       = 128        # 模型 max_seq_length，运行时读取，不写死
max_tokens   = window - 4 # 预留 [CLS] / [SEP]
```

切块在 **token** 单位上进行，`max_tokens` 由运行时从模型实际读取。具体规则：

| 步骤 | 做法 | 解决什么 |
|---|---|---|
| 1 | 按 Markdown 标题（`#`~`######`）解析出小节，并记录**标题路径** | 结构信息不丢，引用可定位 |
| 2 | 每个小节的可用额度 = `max_tokens` **减去它自己标题路径的 token 消耗** | 长标题不会把正文挤出去 |
| 3 | 小节超额度时递归切分：先按段落，再按标点，最后**无标点也硬切**（`_clamp`） | 任何文本都能被切开 |
| 4 | `_clamp` **每切一刀都重新测量一次**，而不是按估算的比例折算 | 计量精确，不依赖字符/token 比值 |
| 5 | 相邻片段带 **40 字符重叠**，且重叠长度会被裁剪到"剩余空间"以内 | 边界上的事实不会两边都查不到 |
| 6 | 切完仍不足 `min_chars`（默认 60）的小节，**合并进上一块**，并保留被吞掉的标题文字 | 避免大量碎片污染检索 |

> **第 5 步曾经有个 bug**：重叠是**在**"是否放得下"的判定**之后**才拼上去的，于是一个刚刚通过检查的片段会被重叠顶回超限。修复方式是让 `_overlap_tail` 先算出真正还剩多少空间。这条逻辑有专门的回归测试（`test_overlap_is_trimmed_when_the_unit_leaves_no_room`）。

### 3.4 运行时的自我验证

后端启动构建索引时，会**再量一遍每个片段的 `embed_text`**，并把结果记入 `chunk_stats`：

```json
{
  "window": 128,
  "max_tokens": 124,
  "count": 190,
  "oversize": 0,
  "avg_chars": 109,
  "split_sections": 183
}
```

| 字段 | 含义 |
|---|---|
| `window` | 从模型实际读取的窗口大小 |
| `max_tokens` | 切块使用的 token 预算 |
| `count` | 检索片段总数 |
| `oversize` | **超过窗口的片段数——这个数必须是 0** |
| `avg_chars` | 平均字符长度 |
| `split_sections` | 被切分成多段的小节数（190 段来自 84 小节，所以绝大多数都被切过） |

这个字典可以在两处看到：

```bash
curl -s --noproxy '*' http://127.0.0.1:8000/health | python -m json.tool
```

CI 里也有一条**专门的前置检查**：`oversize` 不为 0 就直接失败（见 [`TESTING.md`](TESTING.md)）。

### 3.5 退化路径

如果 tokenizer 加载失败（离线环境、依赖缺失），切块会自动退回**字符预算**模式（`RAG_CHUNK_MAX_CHARS`，默认 160），并照常工作。功能不中断，但准确性无法保证——日志里会写明。

## 四、检索：混合检索 + 小切片检索，大段落引用

### 4.1 两级粒度：小切片检索，大段落引用

切得更细带来了一个副作用：**同一小节被切成 4 段后，如果 4 段都被检索到，答案里就会出现 4 遍同一个标题。**

解决办法是**两级粒度**：

| 层级 | 单位 | 用途 |
|---|---|---|
| 检索层 | **片段（chunk）** | 每个向量都完整落在嵌入窗口内，相似度才有意义 |
| 引用层 | **段落（passage）** | 相邻片段按小节重新拼回一段，一段对应一个引用 |

实现是 `group_passages()`：把同 `source` + 同标题路径的命中片段按 `part` 顺序拼起来，相似度取其中最大值（所以**排名不会被打乱**），并标记 `parts = n`。

效果（实测）：问题 `BI-RADS 分级是什么意思？` 命中 5 个片段，合并为 2 个引用，其中第一条是 `乳腺癌知识库 > BI-RADS 分级含义（合并 4 段）`，一段 497 字符的完整释义——而不是标题重复 4 次的碎片。

答案正文里每段独立编号（`[^c1]`、`[^c2]`…），编号与引用列表一一对应。**正文用纯文本渲染，不带 Markdown 语法**——界面是 `whitespace-pre-wrap` 展示的，写 `**加粗**` 只会让用户看到星号。

### 4.2 混合检索：纯向量在缩写和人名面前是弱的

原来的检索是**纯向量**（`IndexFlatIP` + 余弦）。它有一个系统性的盲区，而这个盲区恰好落在这份语料的强项上：

**缩写、数字、人名几乎不携带语义质量。** 句向量模型把「Youden 指数」编码成一个靠近"统计学指标"的模糊位置，于是问题被当成"泛泛地问指标"，排序就飘到措辞最像的那一页去了。词法检索的偏差正好相反——它只认这个词出现过没有。

所以现在两路并行，再融合：

| 阶段 | 做什么 |
|---|---|
| 1 · 稠密 | FAISS 余弦召回 top-N（N = `RAG_RETRIEVE_CANDIDATES`，默认 20） |
| 2 · 稀疏 | 自实现的 **Okapi BM25** 召回 top-N |
| 3 · 融合 | **RRF**（Reciprocal Rank Fusion，`k=60`） |
| 4 · 重排 | 可选，CrossEncoder 重排（见 4.3） |

三个设计决定值得解释：

**BM25 是自己写的，不是引依赖。** 一共三十行公开公式，而更重要的是：它**必须**和词法拒答闸门用同一个分词器。引一个库意味着两套分词，两个"词法信号"会对同一段文本给出不同判断——BM25 排第一的片段，闸门可能判它没有词面依据，用户看到的将是"系统刚刚认定的最佳匹配被拒绝回答"。

**融合用 RRF，不是加权求和。** BM25 的分数没有上界，余弦在 `[-1, 1]`，直接相加需要一个归一化系数——而这个系数本身就是一个没人验证过的可调参数，还会随语料规模漂移。RRF 只吃两路各自的**排名**，不需要任何标定。这也意味着**`RAG_MIN_SIMILARITY`（0.30）不用重新标定**：它是余弦阈值，而 `search()` 返回的第二个元素仍然是**原始余弦**，不是融合分。

**余弦闸门读的是"命中里最好的余弦"，不是 `hits[0]` 的。** 这一条很关键：词法提升会把一个余弦偏低但关键词命中的片段顶到第一位，如果闸门读 `hits[0]` 的余弦，就会出现"因为 BM25 干了它该干的事，所以把一个有据可查的问题拒答了"。反过来，闸门也**不能**读融合分——那是排序用的数，量纲和阈值不是一回事。

**词法闸门则相反：它只读 `hits[0]`。** 这个不对称是刻意保留的，而且它正是 4.3 里那 4 个问题"被诚实拒答"的原因——详见 4.3。

### 4.3 实测：混合检索修好的是什么

`_tools/eval_retrieval.py` 是可复跑的 A/B 工具，同一份索引、只切换配置开关，跑 15 个探针（外加 4 个**必须被拒答**的反向探针）。**每个探针的"期望小节"是从语料里查出来的，不是手写的**——第一版手写了几个小节名，其中三个在语料里根本不存在，结果一次能跑的检索看起来像坏了。

| 模式 | hit@1 | 进 top-5 | 误拒答 | 平均耗时 |
|---|---|---|---|---|
| `dense`（旧行为） | 9/15 | 12/15 | **4** | ~24 ms |
| `hybrid`（默认） | **13/15** | 13/15 | **0** | ~25 ms |
| `hybrid+rerank` | 13/15 | **15/15** | 0 | ~2241 ms |

混合检索修好的 4 个（dense → hybrid）：

```
+ Youden 指数是怎么用的？      -> 判定阈值的作用
+ 约登指数是什么意思？         -> 判定阈值的作用
+ 数据泄漏为什么会让评估失真？   -> 数据泄漏与评估可信度
+ 房颤是怎么回事？            -> 心律失常基本概念
```

注意这四个在**旧模式下全都是被拒答的**（dense 的 4 次误拒答正好就是这 4 个）。但**拒答它的是词法闸门，不是相似度闸门**——这一点值得说清楚，因为直觉上会以为是"没检索到所以拒答"。实测数值：

| 问题 | 旧模式下排第一的小节 | 最高余弦 | 对 `hits[0]` 的词法覆盖率 | 拒答？ |
|---|---|---|---|---|
| `Youden 指数是怎么用的？` | 概率校准与布里尔分数 | 0.4380 | **0.000** | 是 |
| `约登指数是什么意思？` | 概率校准与布里尔分数 | 0.4304 | **0.000** | 是 |
| `数据泄漏为什么会让评估失真？` | 准确率、精确率与 F1 | 0.6099 | **0.000** | 是 |
| `房颤是怎么回事？` | 冠状动脉造影 | 0.4932 | **0.000** | 是 |

四条的余弦**都远高于 0.30 的阈值**，所以相似度闸门从未触发。触发的是词法覆盖闸门：它只读 `hits[0]`（即将用来作答的那一个片段），而 dense 把"一个内容词都不重合的小节"排到了第一——问 `Youden` 却答以《概率校准与布里尔分数》。**闸门是在如实报告它拿到的那段文字不值得作答。真正坏掉的是排序，拒答是诚实的。**

> **一个刻意保留的不对称**：余弦闸门取"命中里最高的余弦"，词法闸门只取 `hits[0]`。看起来应当统一，统一了却会更糟——实测若把覆盖率也改成取最大值，这四条的覆盖率为 0.125 / 0.143 / 0.333 / 0.167，**全部越过 0.12 的阈值**，于是四条**都会被作答**，只是引的是错误的小节。一个"自信地从错误章节引用"的答案，比一句"知识库中没有相关内容"危险得多。这个不对称由 `test_coverage_is_measured_against_the_top_hit_not_the_best_hit` 守着。

换句话说：**误拒答是可见的、可修的；误答是隐形的**。这里选择让错误暴露出来。

BM25 排序把真正含该词的小节顶到第一，两个闸门于是同时满足，四条一起修好，代价约 1 毫秒。对这类产品，**误拒答是最糟的失败模式**：一个答得不太准的答案只是质量问题，一个"没有相关内容"的答复是产品坏了。

另外 4 个反向探针（越界提问）在**三种模式下都被正确拒答**，说明词法通路没有把病种隔离捅穿——这是病种过滤跑在融合之前（`in_scope` 在每个召回器内部各自生效）的直接结果。

### 4.4 重排：实现了，但默认关闭（这是量出来的，不是漏做）

`bge-reranker-base`（CrossEncoder）已经接好：对融合后的 top-N 逐对打分再排序。它在**进 top-5** 上从 13/15 提到 15/15，**hit@1 一个没变**，而每次查询从 25 ms 变成 **2241 ms**——CPU 上约 **90 倍**。

本地路径是这个项目对外承诺"快且零成本"的那条路，让它比用来对照的真实模型调用还慢，是一次看得见的倒退，而换来的排序收益在 top-1 上测不到。所以 `RAG_RERANK_ENABLED` 默认 `false`；需要 top-5 召回（比如答案要引用多段）时打开一行配置即可，然后重跑上面的工具复核。

它同时也是**尽力而为**的，不是硬依赖：模型拿不到（离线容器、空缓存、内存不够）时，检索降级到融合排序继续工作，`/health` 的 `rag_retrieval.rerank_unavailable` 会写明。加载放在**索引构建期**而不是首次提问，否则那几秒（或 1.1 GB 下载）会被记成那个问题的耗时。开启后首次运行需要下载约 1.1 GB。

> **Windows 上的一个坑**：`huggingface_hub` 在 Windows 上创建符号链接可能失败，于是 `snapshots/` 里留下的是**0 字节的文件**，而真正的权重躺在 `blobs/` 里——报错是 `OSError: ... is not a valid JSON file`，看起来完全不像下载问题。删掉 `~/.cache/huggingface/hub/models--BAAI--bge-reranker-base/snapshots` 后设 `HF_HUB_DISABLE_SYMLINKS=1` 重新下载即可（代价是快照变成真实副本，多占约一倍磁盘）。**这个失败会被优雅降级吞掉**，所以它不会报错，只会让重排静默不生效——`/health` 的 `rerank_unavailable` 就是为此存在的。

### 4.5 可观测性：`/health` 会说真话

"我们加了混合检索和重排"是一句读 diff 验证不了的话——尤其是**静默降级**（重排模型没下下来，于是悄悄退回纯向量）和功能正常长得一模一样。所以 `/health` 里多了一节：

```json
"rag_retrieval": {
  "mode": "hybrid",
  "hybrid_enabled": true,
  "bm25": "okapi",
  "rrf_k": 60,
  "candidates": 20,
  "rerank_enabled": false,
  "rerank_model": null,
  "rerank_unavailable": false,
  "last_query": { "mode": "hybrid", "dense": 30, "lexical": 12, "fused": 20, "reranked": 0 }
}
```

`last_query` 是**上一次查询**的实际数字。为什么需要它：检索返回了正确的片段，并不能证明融合起了作用；`dense` 和 `lexical` **同时非零**才能，而那只有在这里看得见。

## 五、检索范围与拒答

### 5.1 病种隔离

每次检索都带 `disease` 参数，只返回该病种的片段。这是"不同病种知识库严格隔离"的落地。

补充一条容易搞错的：**`general` 片段（免责声明与系统说明）对每个查询都是合法的**，所以"范围隔离"的准确含义是"不出现**其他病种**的片段"，而不是"只出现当前病种的片段"。曾经有一条测试断言 `全部 disease == "breast"`，它读起来像同一条保证，实际比设计更严——它一直通过只是因为那条查询恰好没把 general 片段带进 top-5，而 BM25 一上来它立刻失败。靠运气通过的测试比没有测试更糟，所以现在断言的是真正想保证的性质：**不允许出现 `heart` 片段**。

### 5.2 一个曾经让拒答失效的坑

原先的相关性检索有个上限：`fetch_k = min(max(top_k × 6, 20), len(chunks))`。

问题在于：**语料小的时候，任何一句医学问题在词面上都和任何一段医学文本很像。** 于是一个"关于冠心病"的问题，在乳腺癌范围内的 20 个候选名额会被……乳腺癌片段占满？不完全——它会被**看起来相似但最终被病种过滤器全部滤掉**的片段占满，导致过滤后**一个候选都不剩**。

后果很具体：`search()` 返回空 → 拒答逻辑走的是**通用兜底文案**，而那句话说好的"您的问题涉及冠心病，超出当前「乳腺癌」知识库的检索范围，请切换模块"**永远显示不出来**。

**修复**：指定 `disease` 时直接扫全量语料（内存里 190 个向量，毫秒级），不再人为设上限。修复后定制的越界提示正常出现，并且有回归测试守着（`test_scoped_search_never_returns_another_disease_modules_chunks`）。这条修复在混合检索下**依然必须成立**：病种过滤跑在**融合之前**，否则 BM25 就能把另一个病种的片段"捞"回来。

### 5.3 三道拒答闸门

`compose_local_answer()` 依次判断：

| 闸门 | 条件 | 拒答文案 |
|---|---|---|
| 0 · 跨病种 | 问题里出现了**其他病种**的关键词（如乳腺癌范围内问"冠心病"） | 定制文案：说明超出范围 + 指引切换模块 |
| 1 · 语义 | 命中中**最高的原始余弦** < `RAG_MIN_SIMILARITY`（0.30） | 通用兜底 |
| 2 · 词法 | 问题 token 在候选片段中的覆盖率 < `RAG_MIN_TOKEN_COVERAGE`（0.12） | 通用兜底 |

闸门 0 之所以排在前面：**当医学词汇高度重合时，"问题提到了另一个病种"是唯一可靠的信号**，向量相似度和词面重合都区分不出来。

另有一条**问候语**分支：`你好` / `您好` / `hi` / `hello` / `hey` / `在吗`（可带 `！。.？?`）会返回一段引导文案，而不是"没有检索到相关内容，请前往医院就诊"——后者作为对一句问候的回应，读起来像是系统坏了。正则**首尾锚定**，所以「你好，乳腺癌怎么筛查」是正常问题，不会被当成问候。

这条分支在**检索之前**短路，原因有三个，都值得说明：

| 若不短路会怎样 | 后果 |
|---|---|
| 仍然跑一次嵌入 + 向量检索 | 为一句"你好"白花一次嵌入计算 |
| 仍然返回检索到的片段作为"出处" | UI 会在"你好"下面列 5 条毫不相关的知识来源 |
| `use_llm=true` 时仍会进入 LLM 合成分支 | **为一个问候语触发一次付费外部调用**，而注入的上下文与输入毫无关系 |

短路后响应里的 `source` 字段标为 `"greeting"`，与 `"knowledge_base"` / `"refusal"` / `"llm_enhanced"` 并列——
让调用方可以准确区分"回答来自知识库"和"这只是一句寒暄"。问答对比页同理：问候语**不会**被计入 `ungrounded_paths`
（"没有引用"和"有结论却无出处"是两件完全不同的事，把前者算作后者等于把最安全的回答标成最高风险）。

## 六、怎么给知识库加内容

1. **新建或编辑** `knowledge/sources/*.md`（`*.txt` 也会被读取）；
2. **文件名决定病种**——想让新文件归到乳腺癌，文件名里要有 `breast`；不确定就用 front matter 显式指定；
3. **用 Markdown 标题组织**。标题层级会变成引用里的"面包屑"，所以层级要有意义：`# 文档名` → `## 主题` → `### 细分`；
4. **单个小节不要超过 ~150 汉字**。超了也会被自动切开，但主动控制能让检索粒度更干净；
5. **重启后端**（无需重新训练模型）；
6. **验证**：

```bash
# 1) 切块统计：count 应该增加，oversize 必须仍为 0
curl -s --noproxy '*' http://127.0.0.1:8000/health | python -m json.tool

# 2) 新文件是否被识别、归属是否正确
curl -s --noproxy '*' http://127.0.0.1:8000/api/v1/rag/sources | python -m json.tool

# 3) 实际问一句，看引用里有没有你的新标题
```

```bash
# 跑一遍切块测试，确认新内容没有破坏窗口约束
cd backend && PYTHONPATH=. pytest tests/test_chunking.py -v
```

> 知识库全部是公开资料的通俗整理，**不包含任何真实患者数据**。新增内容请沿用这个原则。

## 七、相关配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `KNOWLEDGE_DIR` | `knowledge/sources` | 知识库目录 |
| `EMBEDDING_MODEL` | `paraphrase-multilingual-MiniLM-L12-v2` | 嵌入模型；**换模型时窗口大小会自动重新读取** |
| `RAG_TOP_K` | `5` | 最终返回的检索片段数 |
| `RAG_MIN_SIMILARITY` | `0.30` | 语义闸门（**读原始余弦，不读融合分**） |
| `RAG_MIN_TOKEN_COVERAGE` | `0.12` | 词法闸门（**只按排第一的片段算覆盖率**，见 §4.3） |
| `RAG_HYBRID_ENABLED` | `true` | 关掉即回到纯向量排序（用于复现对比） |
| `RAG_RRF_K` | `60` | RRF 常数，论文取值；只在候选池涨几个数量级时才需要动 |
| `RAG_RETRIEVE_CANDIDATES` | `20` | 融合后保留、交给重排的候选数；**这是延迟的杠杆** |
| `RAG_RERANK_ENABLED` | **`false`** | 默认关闭，理由见 §4.4（25 ms → 2241 ms，top-1 无提升） |
| `RAG_RERANK_MODEL` | `BAAI/bge-reranker-base` | 交叉编码器；开启后首次运行下载约 1.1 GB |
| `RAG_RERANK_MAX_TOKENS` | `512` | 输入上限；片段本身只有 ~124 token，所以它不是延迟杠杆 |
| `RAG_CHUNK_MAX_CHARS` | `160` | **仅在 tokenizer 不可用时的退化预算** |
| `RAG_CHUNK_MIN_CHARS` | `60` | 小于此长度的小节会被合并 |
| `RAG_CHUNK_OVERLAP_CHARS` | `40` | 相邻片段的字符重叠 |

> 注意 `RAG_CHUNK_MAX_CHARS` 是**字符**预算，只在退化路径生效；正常路径用 token 预算，两者不是一回事。

### 一个反直觉的分词行为

分词前会做**去空白 + 全半角归一**，而 `[a-z0-9]+` 按连字符断开，所以：

```
"BI-RADS 4A 是什么意思？"  ->  ['bi', 'rads4a', '是什', '什么', '么意', '意思']
```

`4A` 被并进了前一个拉丁串，产生的是 **`rads4a`**，不是 `rads` + `4a`。这不影响本次检索（语料里同样写着「BI-RADS 4A」，归一化后得到同一个 token），但如果你新增内容时发现某个"带数字的缩写"匹配不上，先看看是不是这个原因。回归测试里专门钉住了这个行为（`test_bm25_indexes_the_same_text_the_lexical_gate_reads`）。
